# Vakil

**An autonomous chargeback defence agent for Razorpay merchants.**
Razorpay AI Buildathon 2026 · Track 2, AI Risk Manager · auto-responder

A chargeback is a countdown timer attached to money that has already left the
merchant's account. Vakil decides whether that money is worth fighting for,
assembles a network-compliant evidence pack, drafts a rebuttal in which every
factual claim traces to a source document, files it through the Razorpay
Disputes API, and records the whole thing to a tamper-evident ledger.

Most merchants lose disputes by default rather than by argument - nobody
assembled the pack before the window closed. Manual representment wins 8-20% of
the time; structured evidence pushes past 50%. That gap is the product.

## Current held-out numbers

Regenerated by CI on every push. n=100, frozen split.

| metric | value |
|---|---:|
| precision | 0.436 |
| recall | 1.000 |
| F1 | 0.607 |
| Brier score | 0.259 |
| escalated to a human | 21 / 100 |

There is deliberately no single "money recovered" headline. Whether Fight-or-Fold
beats fighting everything depends entirely on the filing cost, which is a
parameter, not a result — so the sweep is the deliverable:

| filing cost | uplift vs always-fight | robust? |
|---:|---:|:--:|
| ₹250 (automated marginal cost) | −₹50,089 | no |
| ₹1,600 | −₹9,585 | no |
| **₹2,000 (fully loaded manual cost)** | **+₹3,722** | **yes** |
| ₹2,500 | +₹36,924 | yes |

*Robust* means the win survives charging every escalated case to Vakil as if a
human had fought it. Without that bound, raising the filing cost makes the
numbers improve simply because more hard cases escalate out of the accounting —
which measures abstention, not judgement.

Split by dispute size at ₹2,000, **the small band is the entire effect**
(+₹16,212, robust). There, fighting everything is outright loss-making: a ₹2,000
filing cost against a ₹3,000 dispute cannot pay for itself at achievable win
rates. Large disputes should simply be fought, and the model says so.

The win model has also never been fit — its coefficients are a hand-set prior,
Brier 0.259 with a 0.53 worst-bin gap. That is the largest remaining source of
error in every rupee figure above. Day 6.

## Run it

Linux / macOS:

```bash
make install      # venv + dependencies
make data         # regenerate the 300-case corpus from seed
make test         # 45 unit tests
make eval         # held-out evaluation -> evals/report.md
make sweep        # cost sensitivity   -> evals/cost_sweep.md
make demo         # assess one case, then verify the audit chain
```

Windows PowerShell — `make` is not a Windows command, so
[`make.ps1`](make.ps1) mirrors the same targets:

```powershell
.\make.ps1 install
.\make.ps1 data
.\make.ps1 test
.\make.ps1 eval
.\make.ps1 sweep
.\make.ps1 demo
```

No API keys are needed for any of the above - the entire decision path is
deterministic. Keys are only required once drafting and live filing land.

A single case, with the working shown:

```
case_0001  13.2 Cancelled Recurring Transaction  Rs 3,798.00
deadline CRITICAL (4.0h left)   evidence 100% complete
CE 3.0: no - CE 3.0 applies only to reason code 10.4, this is 13.2

  win probability             0.870
  break-even probability      0.228
  margin over break-even     +0.642
  dispute amount        Rs 3,798.00
  gross expected recovery Rs 3,303.85
  less filing cost         -Rs 250.00
  less arbitration exposure -Rs 104.09
  net EV                Rs 2,949.76

FIGHT  confidence 1.00  auto-file
win estimate 87% clears the 23% break-even for a Rs 3,798.00 dispute by +64%
```

**Break-even** is the whole engine in one number: `p* = (C + X) / (A + X)` for
amount A, filing cost C and arbitration exposure X. The verdict is just
`p_win > p*`; confidence is the distance between them. A small dispute has a
high break-even — only fight when nearly certain. A large one has a low
break-even — worth fighting on thin odds. When `p*` exceeds 1.0, the cost
structure has priced the case out entirely and the engine folds without
deliberating.

## How it is put together

```
ingest → triage → evidence harvest → CE 3.0 → Fight-or-Fold → draft → file → ledger
         └─rules┘  └──model──────┘  └─rules┘  └───rules───┘  └model┘  └──rules──┘
```

The load-bearing design decision: **the model never decides where money goes.**
Claude reads scanned delivery proofs and writes the rebuttal. Triage, CE 3.0
qualification, the EV arithmetic, and the audit chain are ordinary Python with
unit tests. Nothing in `vakil.decide` can hallucinate.

Four things here that are not in the other submissions:

1. **Fight-or-Fold.** Everyone assumes "always fight". Fighting costs money and
   spends dispute-ratio headroom. Two cases with identical odds and different
   amounts get opposite verdicts, and the arithmetic is on screen.
2. **Provenance gate.** Every sentence in the rebuttal must cite a span in a
   source document or it is deleted before filing.
3. **Deterministic CE 3.0.** 2+ prior undisputed transactions, 120-365 days old,
   ≥2 matching identifiers. 40 lines, 9 tests, every rejection names its clause.
4. **Hash-chained ledger.** `vakil verify` walks the chain; editing or deleting
   any historical record breaks it, and `replay` refuses to run on broken history.

## Scope

Defence only. Vakil helps a merchant respond to disputes raised against them.
It contains no capability to initiate, provoke, or manipulate a dispute, and the
corpus generator is an evaluation fixture, not a fraud tool. See
[docs/THREAT-MODEL.md](docs/THREAT-MODEL.md).

All data in this repository is synthetic. No real cardholder, merchant, or
transaction records are present.
