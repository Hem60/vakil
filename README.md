# Vakil

**An autonomous chargeback defence agent for Razorpay merchants.**
Razorpay AI Buildathon 2026 · Track 2, AI Risk Manager · auto-responder

A chargeback is a countdown timer attached to money that has already left the
merchant's account. Vakil decides whether that money is worth fighting for,
assembles a network-compliant evidence pack, drafts a rebuttal in which every
factual sentence traces to a source document, files it through the Razorpay
Disputes API, and records the whole thing to a tamper-evident ledger.

Most merchants lose disputes by default rather than by argument — nobody
assembled the pack before the window closed. Manual representment wins 8-20% of
the time; structured evidence pushes past 50%. That gap is the product.

|---|---:|---:|
| precision | 0.436 | **0.700** |

Calibration chosen by 5-fold cross-validation **inside** the training set —

### There is deliberately no "money recovered" headline

Whether choosing beats fighting everything depends entirely on the filing cost,
which is a parameter rather than a result. So the sweep is the deliverable:

| filing cost | uplift vs always-fight (no arb.) | (arbitration charged) |
|---:|---:|---:|
| ₹250 — automated marginal cost | −₹72,983 | −₹36,983 |
| **₹1,200** | −₹34,978 | **+₹2,622** |
| ₹2,500 — fully loaded manual cost | +₹22,042 | +₹64,442 |

Two accountings because they disagree, and the disagreement is the finding. The
EV engine prices arbitration exposure into every decision; omitting it from the
scoreboard scores the system against a cost it was told to avoid, which
penalises folding specifically. **Robust crossover: ₹2,500 without it, ₹1,200
with.** See [D9](docs/DECISIONS.md).

### Document extraction

21 of 175 documents, 105 fields. Free-tier quota, resumes from a checkpoint.

| outcome | rate | n |
|---|---:|---:|
| correct | 99.1% | 104 |
| **wrong** | **0.9%** | 1 |
| abstained | 0.0% | 0 |

The headline is the **wrong** rate, not the correct rate. An abstention costs a
missing sentence in a letter; a wrong value puts a fabricated fact in a document
filed with a bank. Those are not the same error and are never collapsed.

The single failure is on the photo tier (3.3% wrong there, 0% on clean and
scanned) and on `delivered_to_address` — the hardest documents, the longest
field.

## Five things that are not in the other submissions

**1. Fight-or-Fold.** Everyone assumes "always fight". Everything collapses into
one number — the break-even win probability `p* = (C + X) / (A + X)` for amount
A, filing cost C, arbitration exposure X. The verdict is `p_win > p*`; confidence
is the distance between them. A small dispute needs near-certainty; a large one
is worth fighting on thin odds. When `p*` exceeds 1.0 the case is priced out
entirely and the engine folds without deliberating.

**2. The provenance gate.** The drafter emits sentences that name the facts they
rest on; code resolves each citation against a closed fact index and checks the
asserted value matches. Anything unverifiable is **removed from the letter**.
Post-hoc prose checking would be a second model marking the first one's
homework — this is a lookup a reviewer can read.

**3. Deterministic CE 3.0.** Two prior undisputed transactions, 120-365 days
old, ≥2 matching identifiers. Forty lines, nine tests, and every rejection names
the clause it failed. A missing identifier never counts as a match — absence of
evidence must not be scored as agreement.

**4. Hash-chained ledger.** `vakil verify` walks the chain; editing or deleting
any historical record breaks it, and `replay` refuses to run on broken history.
The filing path's idempotency guard reads this ledger rather than memory,
because the case that matters is a retry after a crash and a crash is what
destroys memory.

**5. Cited requirements, and the gap to reality.** Every dispute condition maps
to what the network requires, each with a citation, each mapped onto the
Razorpay evidence field that would satisfy it. 31 of 100 cases are missing
something required — most often `shipping_proof`.

## How it is put together

```
ingest → triage → evidence harvest → CE 3.0 → Fight-or-Fold → draft → file → ledger
         └─rules┘  └──model──────┘  └─rules┘  └───rules───┘  └model┘ └─rules─┘
```

**The model never decides where money goes.** It appears in exactly two places:
reading scanned delivery documents, and writing the rebuttal. Triage, CE 3.0,
the EV arithmetic, the autonomy gate, the filing gates and the audit chain are
ordinary Python with tests. The one place prose is generated is verified by code
before anything is filed.

Filing is mostly refusals: the verdict must be FIGHT, autonomy must be granted,
the deadline must be open, and it must not already be filed.

Full walkthrough: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Honest limitations

- **The LLM drafters have never run live.** The letters this repository produces
  come from `TemplateDrafter`, which builds sentences from facts with no model —
  and therefore cannot hallucinate by construction. The Anthropic account has no
  credit; the Gemini free tier was spent on extraction. Both model drafters are
  written and schema-tested. ([D13](docs/DECISIONS.md))
- **Extraction runs on Gemini, not Claude.** A funding constraint, not an
  architectural preference. The Claude backend ships either way and the eval
  reports whichever produced the numbers. ([D10](docs/DECISIONS.md))
- **17 of 20 rulebook entries are unverified.** Visa and Mastercard rulebooks
  are licensed documents and are not reproduced here; `data/rulebook/` holds
  summaries written for this project, each citing the rule it summarises. The
  count is printed by `vakil rules` and by the eval report. ([D8](docs/DECISIONS.md))
- **All data is synthetic.** No real cardholder, merchant, or transaction
  records. The corpus generator, its distribution and its biases are documented
  in [docs/DATA-CARD.md](docs/DATA-CARD.md).
- **Real disputes cannot be raised on demand in Razorpay test mode.** The
  bundled mock speaks the documented API shapes and is what exercises the filing
  path; the real client ships regardless.

## Scope

Defence only. Vakil helps a merchant respond to disputes raised against them. It
has no capability to initiate, provoke or manipulate a dispute, never sees a
card credential, and the corpus generator is an evaluation fixture rather than a
fraud tool. See [docs/THREAT-MODEL.md](docs/THREAT-MODEL.md).
