# Data card

## What this is

300 synthetic chargeback cases, generated by
[`data/generator/generate.py`](../data/generator/generate.py), split 200 train /
100 held-out test.

**No real cardholder, merchant, or transaction data is used anywhere in this
repository.** Real chargeback corpora are not obtainable by a student, and
pretending otherwise would be the more dishonest option. What follows is what
the corpus can and cannot support.

Positive rate (representment should have won): **0.43**

Evidence is deliberately patchy, because real merchant systems are:

| slot | present |
|---|---:|
| order record | 100% |
| delivery proof | ~74% of physical goods, 0% of subscriptions |
| — of which signed | ~55% |
| — delivered to a non-order address | ~9% |
| support transcript | ~63% |
| merchant policy | ~86% |
| refund already issued | ~11% |
| prior transaction history | 0-4 records, 22% have none |

Around 8% of cases have an already-closed response window, so the expired path
is exercised on purpose rather than by accident.

## Labels

The ground-truth label - *should this representment have won?* - comes from an
**oracle that reads the case facts directly and never imports `vakil.*`**.
Evaluating a model against labels the model helped produce is circular, and that
circularity is the most common way a hackathon evaluation quietly lies.

Oracle basis per reason code:

| code | wins when |
|---|---|
| 10.4 | CE 3.0 prior relationship qualifies, or delivery was signed and to the order address |
| 13.1 | proof of delivery exists and matches the order address |
| 13.3 | policy on file, correct delivery, and a 35% coin flip - subjective quality claims are rarely rebuttable with documents |
| 13.2 | cancellation terms on file plus a support record |
| 13.6 | a refund confirmation exists |
| 12.6 | distinct order records, 72% |

**Label noise: 8%.** Verdicts are flipped at random at that rate, standing in
for issuer discretion. Real issuers do not decide as a pure function of the
evidence, and a model scoring 1.00 against noiseless labels has learned the
fixture rather than the problem. Both the clean and noisy verdicts are retained
per case (`oracle_verdict`, `should_win`) so the ceiling is measurable.

## Known biases and limitations

Stated plainly, because these bound every number in the eval report.

1. **The oracle is a rule set, so the task is learnable in principle.** Real
   issuer behaviour is messier, less consistent, and influenced by factors the
   merchant never sees. Metrics here are an upper bound on real performance.
2. **Amounts are drawn from six product archetypes** spanning ₹1,899-₹12,499.
   The corpus has no long tail of very small or very large disputes, which is
   exactly the regime where Fight-or-Fold matters most - see D5 in
   [DECISIONS.md](DECISIONS.md). A heavier small-ticket tail is the next
   corpus change.
3. **Reason-code mix is estimated, not sourced.** It reflects a plausible Indian
   card-not-present retailer: fraud claims dominant, non-delivery close behind,
   subjective quality a long tail. It is not derived from published Razorpay or
   NPCI data, because none at this granularity is public.
4. **Identifier drift is modelled with a single parameter.** Real customers
   change devices and addresses in correlated, bursty ways; here drift is
   independent per field, which probably makes CE 3.0 qualification cleaner to
   detect than it is in practice.
5. **Documents are references, not files.** `document_uri` points at fixture
   paths. Until day 5 there are no real scanned PODs to parse, so the extraction
   stage is not yet exercised against realistic image noise.
6. **One merchant, one geography, one currency.** No multi-currency,
   cross-border, or marketplace cases.

## What it is honestly good for

Measuring whether the decision logic behaves sensibly across a controlled range
of evidence conditions, and detecting regressions when it changes. It is not
evidence that Vakil would achieve these numbers on a real dispute inbox, and the
eval report says so on every run.
